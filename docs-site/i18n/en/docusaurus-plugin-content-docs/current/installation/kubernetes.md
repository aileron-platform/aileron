# Kubernetes Quick Installation

This chapter is the installation entry point for a new Kubernetes environment.
The repository does not provide a directly deployable production platform
overlay. The deployment flow must generate
`/run/aileron/platform-values.yaml` with storage, networking, Ingress, TURN,
and security contracts verified for the target cluster.
`helm/aileron/tests/values/platform-*.yaml` files are render-contract fixtures,
not deployment profiles. Before a production deployment, complete these topic
guides:

- [Storage Design](./kubernetes-storage.md)
- [Image Builds and Private Registry](./kubernetes-images.md)
- [Networking, Ingress, TLS, and TURN](./kubernetes-networking.md)
- [Workspace Firewall](./kubernetes-firewall.md)
- [Helm Values Reference](/reference/helm-values.md)

## Prerequisites

- A Kubernetes minor/provider combination that is recorded in the conformance matrix and has actually passed, plus `kubectl`, Helm 3, and an available Ingress Controller.
- The cluster must provide the GA [`discovery.k8s.io/v1` EndpointSlice API](https://kubernetes.io/docs/reference/kubernetes-api/discovery/endpoint-slice-v1/). Conformance fails closed when it is unavailable and does not use the `Endpoints` API.
- Cilium. Production must enable Workspace network isolation with `cilium.enabled=true`; the current firewall attestor requires a UID 0 container with a read-only Cilium socket mount.
- Shared `Filesystem + ReadWriteMany` storage for the Workspace working tree.
- `ReadWriteOnce` storage for Runtime HOME by default; platforms may explicitly select `ReadWriteMany`.
- Shared `Filesystem + ReadWriteMany + Retain` storage for Knowledge Bases.
- Explicit `ReadWriteOnce + Retain` StorageClasses for Manager state, PostgreSQL, and Redis.
- Immutable Aileron image digests for the target architecture, with every node trusting the private Registry CA.
- One public DNS name and TLS Secret for `platformPublicOrigin`.
- Required Secrets for Runtime assertions and Browser credentials. Registry authentication uses either kubelet/node identity or an image pull Secret, depending on the platform.
- DNS and node firewall configuration for built-in TURN, or an ICE JSON Secret when using external TURN.

The production profile does not infer data purposes from `global.storageClass`. Every persistent component must specify its own StorageClass.

## 1. Prepare the Namespace and Secrets

Run all commands below from the cluster administration host:

First prepare these files in a temporary directory with mode `0700`:

```bash
install -d -m 0700 /run/aileron/private-material
```

- `private-key.pem`: An Ed25519 PKCS#8 private key with file mode `0600`.
- `jwks.json`: Contains only the matching public key, whose `kid` exactly matches `runtimeAssertions.activeKid`.
- `browser-credential-keyring.json`: Generated by a controlled secret workflow with mode `0600`, using the schema below. The key material is an unpadded base64url encoding of 32 random bytes.

`jwks.json` must use the following OKP/Ed25519 signing-key schema. `x` is the unpadded base64url
encoding of the 32-byte raw public key, not PEM or DER content:

```json
{
  "keys": [
    {
      "kty": "OKP",
      "crv": "Ed25519",
      "alg": "EdDSA",
      "use": "sig",
      "kid": "workspace-manager-ed25519-v1",
      "x": "<base64url-encoded-32-byte-public-key>"
    }
  ]
}
```

After preparing `openssl` and `jq` on the controlled administration host, use the following commands
to validate the schema, `kid`, and private/public key pair. The commands do not print the private key,
but shell tracing must remain disabled:

```bash
set +x
export ACTIVE_KID=workspace-manager-ed25519-v1

head -n 1 /run/aileron/private-material/private-key.pem \
  | grep -qx -- '-----BEGIN PRIVATE KEY-----'
openssl pkey \
  -in /run/aileron/private-material/private-key.pem \
  -check -noout >/dev/null

jq -e --arg kid "${ACTIVE_KID}" '
  ([.keys[] | select(.kid == $kid)] | length) == 1 and
  any(.keys[];
    .kid == $kid and
    .kty == "OKP" and
    .crv == "Ed25519" and
    .alg == "EdDSA" and
    .use == "sig" and
    (.x | test("^[A-Za-z0-9_-]{43}$"))
  )
' /run/aileron/private-material/jwks.json >/dev/null

EXPECTED_X="$(
  jq -er --arg kid "${ACTIVE_KID}" \
    '.keys[] | select(.kid == $kid) | .x' \
    /run/aileron/private-material/jwks.json
)"
ACTUAL_X="$(
  openssl pkey \
    -in /run/aileron/private-material/private-key.pem \
    -pubout -outform DER 2>/dev/null \
  | tail -c 32 \
  | openssl base64 -A \
  | tr '+/' '-_' \
  | tr -d '='
)"
test "${EXPECTED_X}" = "${ACTUAL_X}"
unset EXPECTED_X ACTUAL_X ACTIVE_KID
```

Set `runtimeAssertions.activeKid` to the same `kid`. The production PKI or secret workflow must
generate these two materials directly. This command only validates them before deployment; it does
not generate or rotate keys.

The Browser credential keyring uses a separate secret with this schema:

```json
{
  "algorithm": "hkdf-sha256-v1",
  "activeKeyId": "browser-credential-v1",
  "keys": {
    "browser-credential-v1": "<base64url-encoded-32-byte-secret>"
  }
}
```

The repository's `workspace-manager/scripts/generate_runtime_assertion_keys.py` is currently a Docker development initialization tool, not the production PKI contract. Production must use the organization's PKI or secret manager to generate and retain the matching assertion pair and Browser keyring.

Then create the namespaces and Secrets:

```bash
export NAMESPACE=workspace-system
export TURN_NAMESPACE=aileron-turn-system

kubectl create namespace "${NAMESPACE}" \
  --dry-run=client -o yaml | kubectl apply -f -

kubectl create secret docker-registry registry-pull \
  --namespace "${NAMESPACE}" \
  --docker-server="${HARBOR_REGISTRY}" \
  --docker-username="${HARBOR_USERNAME}" \
  --docker-password="${HARBOR_PASSWORD}"

kubectl create secret generic runtime-assertion-signer \
  --namespace "${NAMESPACE}" \
  --from-file=private-key.pem=/run/aileron/private-material/private-key.pem

kubectl create secret generic runtime-assertion-public-jwks \
  --namespace "${NAMESPACE}" \
  --from-file=jwks.json=/run/aileron/private-material/jwks.json

kubectl create secret generic browser-credential-keyring \
  --namespace "${NAMESPACE}" \
  --from-file=keyring.json=/run/aileron/private-material/browser-credential-keyring.json

kubectl create secret tls aileron-platform-tls \
  --namespace "${NAMESPACE}" \
  --cert=./tls.crt \
  --key=./tls.key
```

With built-in TURN, a private Coturn image, and Secret-based Registry
authentication, the Coturn DaemonSet also references `global.imagePullSecrets`,
but Kubernetes Secrets cannot cross namespaces. The Chart does not copy the
Registry Secret. Before installation, pre-create the Coturn namespace, mark it
as owned by this Helm release, and create a Secret with the same name:

```bash
kubectl create namespace "${TURN_NAMESPACE}" \
  --dry-run=client -o yaml | kubectl apply -f -
kubectl label namespace "${TURN_NAMESPACE}" \
  app.kubernetes.io/managed-by=Helm --overwrite
kubectl annotate namespace "${TURN_NAMESPACE}" \
  meta.helm.sh/release-name=aileron \
  meta.helm.sh/release-namespace="${NAMESPACE}" \
  --overwrite

kubectl create secret docker-registry registry-pull \
  --namespace "${TURN_NAMESPACE}" \
  --docker-server="${HARBOR_REGISTRY}" \
  --docker-username="${HARBOR_USERNAME}" \
  --docker-password="${HARBOR_PASSWORD}"
```

Skip this procedure when TURN is disabled, uses the external provider, or image
pull access comes from kubelet or node managed identity. The two-namespace
Secret procedure applies only to Secret-based Registry authentication; the
Chart does not yet copy or rotate the Secret automatically.

Do not commit Secret values, kubeconfig files, private keys, or deployment values containing credentials to Git.

The `registry-pull` Secret applies only to an external private Registry that
requires Kubernetes Secret authentication. Omit both the Secret and
`global.imagePullSecrets` when EKS/ECR, GKE/Artifact Registry, or AKS/ACR is
already authorized through kubelet or node managed identity.

The Helm release namespace must equal
`kubernetes.workspaceRuntimeNamespace`; the Chart rejects a mismatch at render
time. A Secret-based external Registry needs one `registry-pull` Secret in this
shared namespace for Chart workloads and Workspace ServiceAccounts. Kubernetes
Secrets cannot be referenced across namespaces, and the Chart does not copy
Registry credentials.

## 2. Create Deployment Values

Combine the platform profile with a values file that is excluded from version control:

```yaml
global:
  imagePullSecrets:
    - name: registry-pull

platformPublicOrigin: https://aileron.apps.example.com

oidc:
  issuerUrl: https://login.example.com/realms/aileron
  clientId: aileron-manager

ingress:
  enabled: true
  className: "<ingress-class>"
  useDefaultClass: false
  tlsMode: kubernetesSecret
  tlsSecretName: aileron-platform-tls
  annotations: {}

runtimeAssertions:
  issuer: workspace-manager
  activeKid: workspace-manager-ed25519-v1
  privateKeySecretName: runtime-assertion-signer
  publicKeySetSecretName: runtime-assertion-public-jwks

browserCredentials:
  existingSecretName: browser-credential-keyring
  key: keyring.json
  revision: 1

cilium:
  enabled: true
```

Complete the image digests, StorageClasses, strong passwords, and TURN settings according to the topic guides. Keep `global.imagePullSecrets` empty when using platform-native Registry identity.

`ingress.annotations` applies only to the single platform Ingress. The deployment profile supplies
the values required by AWS Load Balancer Controller, GKE Ingress, Application Gateway, NGINX, or
another controller. Product defaults disable public Ingress and assume no specific controller.
Runtime, Browser, and Canvas expose internal Services only; Frontend's gateway routes fixed
`/workspaces/{uuid}/runtime|browser|canvas` paths to them.

Select a controller with `ingress.className`, a provider class annotation, or an intentionally configured
cluster-default IngressClass with `ingress.useDefaultClass: true`. Use
`tlsMode: kubernetesSecret` for TLS terminated by a Kubernetes Secret. When AWS
ACM, a GCP pre-shared certificate, or another controller policy manages TLS,
use `tlsMode: controllerManaged` and keep `tlsSecretName: ""`.

## 3. Pre-deployment Checks

The deployment flow must point `PLATFORM_VALUES` to the target cluster's generated and verified platform overlay:

```bash
export PLATFORM_VALUES=/run/aileron/platform-values.yaml

helm lint helm/aileron \
  -f "${PLATFORM_VALUES}" \
  -f /run/aileron/deployment-values.yaml

helm template aileron helm/aileron \
  --namespace workspace-system \
  -f "${PLATFORM_VALUES}" \
  -f /run/aileron/deployment-values.yaml \
  >/tmp/aileron-rendered.yaml

kubectl apply --dry-run=server -f /tmp/aileron-rendered.yaml
```

`PLATFORM_VALUES` must be the provider-neutral or provider-specific production
profile for this cluster. Do not reuse another environment's GID,
StorageClasses, or administrator settings. Files under
`helm/aileron/tests/values/platform-*.yaml` are Helm render fixtures only; they
are not deployable profiles and cannot replace provider conformance against the
real CSI, CNI, and admission stack.

Success criteria:

- Lint, rendering, and server-side dry-run all succeed.
- The rendered output contains no floating image tags.
- Every persistent component has a dedicated StorageClass.
- Built-in TURN is the only workload permitted to use `hostNetwork`, and only the configured relay range is allowed.
- TURN credentials are referenced only through Secrets; their actual values do not appear in Pod arguments.
- With built-in TURN and a private Registry, both `workspace-system` and `coturn.namespace` can read a same-named Secret selected by `global.imagePullSecrets`.

## 4. Install

```bash
helm upgrade --install aileron helm/aileron \
  --namespace workspace-system \
  --create-namespace \
  -f "${PLATFORM_VALUES}" \
  -f /run/aileron/deployment-values.yaml \
  --atomic \
  --timeout 15m
```

## 5. Minimum Acceptance

```bash
kubectl get pods,pvc,ingress -n workspace-system
export RELEASE=aileron
for component in frontend workspace-manager workspace-operator; do
  kubectl wait deployment \
    --namespace workspace-system \
    --selector="app.kubernetes.io/instance=${RELEASE},app.kubernetes.io/component=${component}" \
    --for=condition=Available \
    --timeout=10m
done
kubectl get jobs -n workspace-system
helm status aileron -n workspace-system
```

Every platform Pod should be Ready, every PVC should be Bound, and the Helm release should be `deployed`. Then create a test Workspace and confirm that Runtime, Browser, and Canvas each become Ready after the initial bootstrap completes.

## Upgrade

Save the current revision and values, then upgrade with new immutable digests:

```bash
helm history aileron -n workspace-system
helm get values aileron -n workspace-system -o yaml \
  >/run/aileron/previous-values.yaml

helm upgrade aileron helm/aileron \
  --namespace workspace-system \
  -f "${PLATFORM_VALUES}" \
  -f /run/aileron/deployment-values.yaml \
  --atomic \
  --timeout 15m
```

## Rollback

When only Deployments and values changed and the data contract did not:

```bash
helm rollback aileron <revision> \
  --namespace workspace-system \
  --wait \
  --timeout 15m
```

If the database schema, CRD, or PVC contract changed, `helm rollback` alone is insufficient. Restore matching PostgreSQL/NFS snapshots, CRDs, and image digests together. Knowledge Bases and platform state should use Retain StorageClasses so release operations do not reclaim data directly.
