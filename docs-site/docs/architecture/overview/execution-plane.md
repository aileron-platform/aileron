# Execution-Plane 生命週期與安全機制

本文件說明 Workspace execution plane（Runtime、Terminal、Browser、Canvas）在 lifecycle、Knowledge Base mount、權限撤銷與 Browser pairing 等情境下共用的內部收斂機制、durable job 模型與安全邊界。使用者可見行為（狀態、按鈕、常見情境）請見 [Workspace 生命週期](/features/workspace/lifecycle-and-access) 與 [Workspace 與知識庫權限](/features/knowledge-base/sharing-and-permissions)。Canvas workload 內部解析 manifest、啟動 renderer 的 management-server 命名澄清請見 [Canvas Protocol](/architecture/overview/canvas/protocol)。

:::info 實作與平台驗證狀態
本頁描述 application、Docker、Workspace CR、Operator 與 Helm 共同遵守的可攜契約。Helm render、安全 assertion、任意 UID image preflight 或本機測試都只是前置檢查，不等於 EKS、GKE、AKS、OCP、RKE2 或原生 Kubernetes 的實機認證。每個目標環境仍須以實際叢集、CSI 版本、CNI 與安全政策執行 conformance runner。
:::

## Control-plane availability gate

Frontend 在掛載任何 Workspace execution-plane Provider 前，先查詢不依賴 Runtime Pod、Ingress 或 WebSocket 的 Manager endpoint：

```http
GET /api/v1/workspaces/{workspaceId}/availability
```

只有 `availability=ready` 才可建立檔案、Git、Terminal、Agent、Thread、Browser 與 Canvas query 或連線。初始 availability 尚未解析時，前端先以 500ms 延遲隱藏提示卡，但 gate 仍保持關閉；超過門檻才掛載檢查提示，且 ready 路徑提供 500ms 最短可見時間。已知的非 ready 或錯誤不受最短時間延遲。其餘狀態只會掛載提示頁與單一 Manager availability observer；它會依經上下限約束的 `retryAfterMs` 輪詢，對穩定的 `401`、`403`、`404`、`409`、`423` 不做自動 retry。狀態中途失效時，observer 會先取消該 Workspace 的 execution-plane query、卸載 Provider 並關閉 WebSocket，再導向提示頁。恢復後必須使用最新 `runtimeInstanceId`，不得沿用已失效的 generation URL、query cache 或 credential。

Manager 完成授權後才回傳 `allowedActions`。`start`、`retry` 與 `rebuild` 使用下列 control-plane endpoint；`return` 只由前端返回安全列表，不送到 execution plane。永久刪除不混入一般 lifecycle action，改由 availability response 的 `deletionProjection` 表達 Owner-only `delete`／`retry`、後端確認的 `deletion.phase` 與 `404` completion。

```http
POST /api/v1/workspaces/{workspaceId}/availability/actions/{action}
```

### 執行平面漂移

執行平面漂移表示控制平面仍宣稱目前 generation 可用，但該 generation 的 Runtime、Browser 或 Canvas Pod／Container 不存在、部分缺失或 workload identity 不符。它不是 Workspace 刪除，也不是 provider 暫時無法觀測；只有在沒有進行中的 lifecycle job，且平台已確認實體 workload 與目前 generation 不一致時才成立。

漂移是 Workspace 全域 fail-closed 狀態。Availability Gate 會先卸載 execution-plane Provider、取消相關 query 並關閉 WebSocket，不讓 Gateway 繼續把請求送往失效 hostname。平台不自動重建、不自動刪除 Workspace DB，也不提供 start、retry 或 rebuild；Owner 只取得永久刪除入口，其他使用者只取得聯絡 Owner 或平台管理員的提示。

Workspace DELETE 對已消失的 workload 採冪等 absence semantics：不存在的 Pod／Container 視為該資源已清理，流程繼續刪除其餘 execution-plane 資源、Workspace 控制面資料、持久資料與權限。只有明確 DELETE intent 能進入這個不可逆流程，漂移觀測本身不授權資料刪除。

### Frontend Entry Projection Boundary

Frontend 將身份確認、Workspace authorization 與 availability machine 的目前事實投影為固定三階段 Entry Flow：Identity、Workspace、Execution。這個投影層不取代任何權威來源，也不解析 provider response 或例外原文；畫面只呈現有限狀態、當次 `allowedActions` 與穩定 `reasonCode`。

Entry Gate 在 Workspace authorization 尚未完成或 availability 尚未確認前，不掛載 execution-plane Provider、query 或 WebSocket。`ready` 且 generation 有效後才交給 Workspace Shell；之後的功能 lazy loading 留在 shell 的內容區。一般 availability refresh 不重新接管已掛載的 shell，只有確認撤權、Workspace identity 改變或 generation fence 失效才清理舊 execution plane 並重新進入 Gate。

`stopped` 不會由前端自動啟動，`refresh` 只重新讀取 availability，`rebuild` 必須經使用者確認；所有 lifecycle mutation 仍由 Manager API 的 `allowedActions` 與既有 authorization contract 決定。

永久刪除使用 `DELETE /api/v1/workspaces/{workspaceId}`；請求接受後由平台依序收斂 Automation cancellation、stop 與 delete。刪除期間 Gate 只顯示 phase progress，失敗保留 Workspace 並提供 Owner retry，`not_found` 才是完成訊號。

`401/403` 不得附帶 lifecycle、revision 或 workload identity。Browser readiness 只阻擋 Browser；KB mount syncing／degraded 只影響 `/knowledge` 與掛載管理，兩者都不能把健康的 Workspace 誤判為全域不可用。

## Durable job 與 recovery

Lifecycle、Knowledge Base mount reconcile 與 access recycle 共用同一個 durable job repository：

- 狀態為 `queued`、`running`、`succeeded`、`failed` 或 `superseded`。
- 每次 claim 具有 lease、heartbeat 與新的 fencing token。
- 較新的 queued revision 會終結 superseded queued lineage，再建立有自己 correlation root 的 successor。
- running job 期間出現新 mutation 時，保留 running row 與最新 queued successor；先前的 job 完成時若 desired 已前進，只能標 `superseded`。
- broker publish 失敗、worker crash 或 lease 過期時，recovery sweep 會重新派送或 reclaim。
- stale claim token 不能再執行 destructive side effect 或提交 observed state。

執行層使用 Celery，但 Celery message 不是正確性的來源：worker 只接收 `job_id`，每次都重新從 PostgreSQL 讀取目標 revision 與完整 desired state。唯一 Celery Beat 負責週期性 recovery／dispatch；重複 delivery 仍由 DB claim token、lease、heartbeat 及 Workspace lock 收斂成單一 side-effect owner。這條 Celery 路徑不負責 Automation 排程；Automation 使用 Manager 內的 asyncio／PostgreSQL scheduler。

## 元件 revision 收斂

Workspace 以 bootstrap、Runtime、Browser、Canvas 四組 desired／observed revision 表示目標與實際狀態。Durable job 會保存 `targetComponent` 與 `targetRevision`；worker 執行前後都重新比對資料庫 fence。較早 revision 只能標成 `superseded`，不能覆寫最新狀態。

| 事件 | 變更的 revision | 影響範圍 |
| --- | --- | --- |
| 首次建立 | bootstrap與三個component | Runtime／Terminal ready後才放行Browser與Canvas |
| 重啟Runtime | runtime | 只替換Runtime／Terminal |
| 重啟Browser | browser | 只替換Browser |
| 重啟Canvas | canvas | 只替換Canvas |
| attach／detach KB、修改 alias | mount candidate 與 runtime | 由 Runtime 驗證 candidate，不替換 Browser／Canvas |
| 撤銷 Runtime operation | access 與 runtime | 由 Runtime 收斂 access，不替換 Browser／Canvas |

元件重啟順序為：同一transaction增加desired revision並建立component job、以claim lease取得side-effect ownership、只終止指定workload、建立同元件新workload、驗證identity與readiness，再更新observed revision。Browser或Canvas失敗只回報該元件`Error`，不刪除Workspace CR，也不回收健康的兄弟元件。

Terminal與agent位於Runtime workload，不是第四個Deployment或container。若無法證明指定 workload 已終止，該元件維持`error`且observed revision不前進。

`stopped` 或 lifecycle `error` 接受的 attachment mutation 會保存完整 candidate snapshot 與 desired revision，延後到下一次 start 收斂；不會因 attach 自動啟動 Workspace。`stopping` 與 `deleting` 拒絕新的 attachment mutation。

### Last-known-good mount saga

每次 attach、rename 或 detach 都從最後一個已驗證的 `active_snapshot` 建立完整 `candidate_snapshot`。Manager 在寫入 candidate 前會檢查 alias、KB UUID、權限、PVC／subPath、目錄、symlink 與 collision，並在同一 transaction 寫入 desired revision、audit 與 durable job。

Runtime／Operator 套用 candidate 後，只有在 readiness probe 與 mount verification 都成功時，Manager 才將 candidate promote 成新的 active snapshot 並推進 observed revision。失敗時會保留目前 active snapshot、記錄 `failed_snapshot` 與 stable error code，進入 compensating；確認 active snapshot 可用後才標示 degraded。不能把「API 已接受」或「Runtime restart 完成」當成 mount 已套用。

Attachment API 與 Workspace detail 提供 last-known-good 狀態：

```json
{
  "knowledgeBaseMountSync": {
    "status": "degraded",
    "desiredRevision": 12,
    "observedRevision": 11,
    "lastKnownGoodRevision": 11,
    "errorCode": "WORKSPACE_KB_MOUNT_RECONCILE_FAILED",
    "compensating": false
  }
}
```

通用 Runtime access gate 會驗證有效 principal、endpoint action 對應的 Workspace OperationId、目前 `allowedOperations`、lifecycle readiness、access generation 與 current `runtimeInstanceId`。Reader 只允許安全 read projection；mutation／execution action 需要 Manager、Owner 或 Platform Admin：

```http
GET /api/v1/workspaces/{workspace_id}/runtime-access?action=<action>&runtimeInstanceId=<current-runtime-instance-id>
Authorization: Bearer <token>
```

mount revision 不再是 files、version control、Terminal、Agent、Thread、Browser 或 Canvas 的全域 access gate。只有 `/knowledge` 與掛載管理呼叫明確的 knowledge-mount gate；一般 Workspace detail 在 syncing／degraded 仍回 `200`，讓 UI 顯示 i18n 對應的 stable error、last-known-good revision 與合法恢復動作。

Direct／group share、群組成員、帳號、Owner、Platform Admin 或 Public KB consumer access 變更時，Manager 提升 generation，讓 cached URL 與 assertion 立即失效，並終止不再允許的 execution-plane session。

## 零複製唯讀掛載

每個 Knowledge Base 只有一份 canonical filesystem 資料：

```text
Canonical KB root
├── <kb-a>/
├── <kb-b>/
└── <kb-c>/
       │
       ├─ Workspace Manager：RW，管理 canonical 內容
       │
       └─ Workspace Runtime：逐一 RO 掛載
          ├── /knowledge/product -> <kb-a>
          └── /knowledge/runbook -> <kb-c>
```

系統不會建立 Workspace copy，也不使用 materializer、projector、KBFS sidecar、NFS namespace controller、自製 CSI 或 FUSE。

### Docker

Manager 以 RW 存取 canonical KB root。Runtime 只把經驗證的 `<kbId>` host 目錄 bind 到 `/knowledge/<alias>`，每個 bind mount 固定 `read_only=true`。

### Kubernetes

Manager 與 Runtime 使用同一個 `Filesystem + ReadWriteMany` KB PVC：

- Manager 掛載 canonical root，具寫入能力。
- Runtime 依 attachment 建立 `subPath=<kbId>`。
- 每個 Runtime `volumeMount` 固定 `readOnly: true`。
- Manager、Operator、Workspace CR、Runtime 與 PVC 位於同一個平台管理的 `workspaceRuntimeNamespace`／OpenShift Project。

PVC access mode 只描述配置與排程能力，不等同 container 內的唯讀保護；真正的邊界仍是 `volumeMount.readOnly`。

## Runtime PostgreSQL 與 credential 邊界

Runtime 狀態不寫入 Workspace／NFS，也不共用 Manager 的平台資料表權限。每個 Workspace 在 Manager 的 PostgreSQL database 內有一個由 Workspace ID 決定、跨 restart 保留的專屬 schema；每個 Runtime instance 則使用不同的 login。Manager 以只掛載在自身的 HMAC key 衍生 instance password，Runtime 不會取得這把衍生根金鑰。

Runtime instance login 不是平台 DB 管理帳號。它不具 `SUPERUSER`、`CREATEDB`、`CREATEROLE`、`INHERIT`、`REPLICATION` 或 `BYPASSRLS`，只取得 database `CONNECT`，預設 `search_path` 固定為自己的 Workspace schema 與 `pg_temp`；平台不會授予它 Manager `public` schema 內資料表的權限。新 Runtime instance 啟用時，Manager 會終止 superseded login 的連線、移轉該 Workspace schema ownership，並停用及刪除 superseded login。

`AILERON_RUNTIME_CONTROL_TOKEN_FILE` 是另一條邊界。唯讀檔案內容是 Runtime-instance-scoped opaque token，明文只交給該 Runtime；Manager database 只保存 digest，且驗證時同時比對 Workspace ID、current Runtime instance 與 lifecycle 狀態。它只能呼叫該 Workspace 的 Manager automation-control endpoints，不是使用者 access token，也不是跨 Workspace 或平台共用的 token。

Kubernetes 會為每個 Workspace 維護一個 `Opaque` Runtime Secret，內容固定只有：

| Secret key | Runtime 環境變數 | 用途 |
| --- | --- | --- |
| `state-database-url` | `AILERON_RUNTIME_STATE_DATABASE_URL_FILE` | 目前 Runtime instance 的 PostgreSQL login 與固定 Workspace schema |
| `runtime-control-token` | `AILERON_RUNTIME_CONTROL_TOKEN_FILE` | 呼叫該 Workspace automation-control endpoints 的 opaque token |

這個 Secret 只以唯讀 volume 掛載至 Runtime container，再由 `*_FILE` 變數指向檔案；Browser／Canvas 不會取得。Manager 的 credential derivation key、Ed25519 private key、平台 database credential 與 Redis credential 都不會放進此 Secret。Docker 使用同樣的唯讀 Secret file 契約。

Lifecycle 對 schema、login、token 與 Secret 的處理如下：

| 事件 | PostgreSQL schema | Runtime instance login／token | Kubernetes Runtime Secret |
| --- | --- | --- | --- |
| start | 不存在時建立，存在時沿用 | 建立新 login 與 opaque token | 建立或更新，只有兩個固定 key |
| Runtime component restart | 保留資料與同一 schema | 終止 superseded 連線並旋轉 login、password、token | 以新Runtime revision值更新 |
| Browser／Canvas component restart | 保留 | 不變 | 不變 |
| stop | 保留，供下次 start 使用 | 終止連線並將 login 設為 `NOLOGIN`；清除 current token fence | 保留；Workspace CR與PVC也保留 |
| delete Workspace | 在 target workload 已證明不存在後 `DROP SCHEMA ... CASCADE` | 終止連線並刪除該 Workspace 全部 Runtime instance role | 刪除 |
| provisioning 失敗 | 不開放 Runtime 入口 | 停用失敗 Runtime instance login 與 token fence | 刪除失敗 Runtime instance 的 Secret |

因此，Runtime restart保留Runtime資料但旋轉credential；Browser與Canvas restart不觸碰Runtime資料庫credential。stop保留CR、PVC與schema，只有delete才移除持久資料。

## Browser connectivity evidence ownership

Browser component readiness 與 Browser TURN connectivity 是兩個獨立狀態。Pod probe 只證明 Neko
process 可服務；`status.browserConnectivity` 則由 Operator 聚合兩條資料路徑：Browser Pod 內
sidecar 的 backend relay evidence，以及 Connectivity Evidence Gateway 保存的 required external
vantage evidence。每筆 evidence 都綁定 TURN Reachability Profile revision、credential revision、
observed time 與 expiry。

Operator 是 connectivity state 的唯一 writer。Manager 將 CR status 投影至 Workspace detail 與
資料庫，並只在新 Browser access admission 檢查 `ready` 與 freshness。使用 `turnRest` 時，
Manager 會在每次核發 Browser access 時以安裝層保管的 shared secret 產生 Workspace-scoped
短效 `iceServers`；Browser Pod 內的 sidecar 也會在每次 backend probe 產生新的短效憑證，
且探測身分綁定 Workspace ID。Neko container 不持有 TURN REST shared secret。

Frontend 不自行推論 TURN readiness；它以 access response 的 `iceServers` 覆寫 Neko 啟動時
回傳的 ICE 設定，並只針對該 access 建立一個可見期間內的 Neko generation。失敗時以
bounded、serialized、fresh-access recovery 替換完整 generation，因此每次重建都會重新經過
admission 並取得新憑證。健康的既有 session 不因後續 evidence 到期而被強制中斷。

`workspace-operator/internal/controller/turn_probe.go`、
`workspace-operator/internal/controller/connectivity_evidence_gateway.go`、
`workspace-manager/app/modules/workspace/browser_credential_access.py` 與
`workspace-manager/app/modules/workspace/browser_turn_credentials.py`、
`frontend/src/features/workspace/features/browser/hooks/useBrowserAccessRecovery.ts`。

## Browser extension pairing 安全

Chrome extension 不持有 Manager service token、drain 私鑰或長期 pairing token。流程如下：

1. 使用者在 Workspace UI 主動連線；Manager 先以 `browser_automation` action 檢查有效 principal、平台／Workspace 角色交集、access revision 與 Browser workload identity。
2. Manager 簽發最長 60 秒、Ed25519／EdDSA、單次 `jti` 的 pairing assertion。claims 綁定 actor、Workspace、`runtimeInstanceId`、Browser container ID／Pod UID、pairing session、audience 與有效期限。
3. Frontend 只向部署時固定的 extension ID 傳送 external message。未設定 extension ID 時不顯示連線入口；extension manifest 只允許明確設定的可信 frontend origin，非 loopback 來源必須使用 HTTPS。
4. Pairing assertion 不放在 URL query、DB、job metadata、browser storage 或 log。extension 只在記憶體保留待使用 assertion，建立 WebSocket 時經 `Sec-WebSocket-Protocol` 傳送並立即消耗。
5. Runtime 以唯讀 JWKS 驗證 signature、`kid`、issuer、audience、action、Workspace、current `runtimeInstanceId`、期限與 single-use `jti`，再把完整 signed identity 綁到該 relay socket。
6. 第二個有效 extension socket 會取代前一個連線；disconnect、Browser replacement 或 access revoke 都會清除 socket、pairing identity、pending CDP request 與使用者 relay connection。已失效的 Browser identity、過期或 replay assertion 一律拒絕。

Browser workload 可在同一個`runtimeInstanceId`內獨立替換。Manager以Browser desired／observed revision、workload identity與current runtime instance共同做身分fence。

## Ed25519 金鑰部署前提

Docker 開發流程會在 host data directory 建立 Ed25519 private key 與 public JWKS；Kubernetes 不會替正式環境產生金鑰，必須在 `workspaceRuntimeNamespace` 預建兩個 Secret：

| Helm value | Secret 必要 key | 掛載者 |
| --- | --- | --- |
| `runtimeAssertions.privateKeySecretName` | `private-key.pem` | 只掛載到 Manager |
| `runtimeAssertions.publicKeySetSecretName` | `jwks.json` | Manager 驗證配對，Runtime／Terminal 驗章 |

`runtimeAssertions.activeKid` 必須存在於 JWKS，且該 public key 必須與 `private-key.pem` 配對。缺檔、重複 `kid`、未知 active `kid`、私鑰出現在 JWKS 或公私鑰不符時，Manager 拒絕簽發 assertion，使 drain／pairing fail closed；Runtime／Terminal 也會在 JWKS 無法驗證時拒絕 assertion。

## Kubernetes workload 身分邊界

每個 Workspace 的 Runtime、Browser 與 Canvas 共用一個專屬 `workspace-workload-<workspaceId>` ServiceAccount。它沒有任何 Role／RoleBinding，ServiceAccount 與三個 Pod template 都設定 `automountServiceAccountToken: false`，因此 Workspace 內的程式無法把 Kubernetes ServiceAccount token 當成額外的權限來源。

這個 ServiceAccount 只隔離 Kubernetes API 身分，不改變 Workspace／KB 應用層授權，也不授予 NFS 額外能力。檔案可見性仍由「Workspace attachment grant + Runtime 唯讀 `subPath` mount」決定；NFS／CSI 存取則由 PVC、node mount、effective UID／fsGroup 與 backend export policy 決定。

動態 Workspace Ingress 預設關閉。此時三個 workload 仍可透過 cluster-internal Service 互通，Operator 會移除 Runtime／Browser／Canvas Ingress；開啟或關閉 Ingress 不需要重建 Workspace execution plane。外部入口、獨立驗證 StorageClass 與部署設定請參考 [Kubernetes 部署](/installation/kubernetes)。

workspace-operator依Workspace CR管理Runtime／Browser／Canvas的Deployment／Service、Workspace RWX PVC、Ingress與可選的CiliumNetworkPolicy。每個Deployment使用自己的component revision annotation；只有Runtime帶instance、mount與access fence。status分別回報observed revision、phase、reason、error、Pod UID與transition time，bootstrap另有獨立狀態。stop將replica縮為零但保留CR與PVC；delete才執行finalizer與持久資源清理。

## 防火牆 desired／observed 收斂

Manager 的 Firewall API 分別保存 Runtime 與 Browser 規則。`PUT /api/v1/workspaces/{workspaceId}/firewall` 只代表 desired state 與 durable firewall command 已成功寫入，不代表 CiliumNetworkPolicy 已套用。Firewall resource 的 `revision` 同時是 desired revision 與下一次寫入的 CAS 基準；每次 durable command 另有不可重用的 delivery ID，Workspace annotation、Workspace firewall status 與所有 CNP 必須精確相符。

Operator 會在每個 CNP top-level Rule 的 spec 寫入該 delivery 專屬 marker。每個節點的 firewall attestor 只透過本機 `/var/run/cilium/cilium.sock` 讀取 endpoint `policy.realized`，逐一證明 selected Pod UID、CiliumEndpoint UID／endpoint ID、CNP UID／name／generation、target revision、delivery ID、realized policy revision、agent incarnation 與時效性，並確認每個 Rule marker 都出現在相同 CNP identity 的 `derived-from-rules`。只有所有 selected endpoint × matching CNP 都有 fresh exact attestation，Operator 才推進 observed revision；CNP `Valid` condition、generation、resourceVersion、`status.nodes` 或 CiliumEndpoint `enforcing` 都不能單獨證明已套用。

| `syncStatus` | 意義 | UI 行為 |
| --- | --- | --- |
| `pending` | durable command 已建立，尚待 worker claim | 停用重複儲存並輪詢，不顯示成功 |
| `applying` | worker 已開始收斂，Operator 尚未確認相同 revision | 停用重複儲存並輪詢，不顯示成功 |
| `applied` | observed 已追上 desired，且所有 endpoint × policy 的本機 `policy.realized` attestation 仍精確且未過期 | 顯示已套用 |
| `error` | command、CR apply 或 Operator reconcile 失敗 | UI 顯示套用失敗，保留 desired 輸入與 i18n stable error，透過 `POST /api/v1/workspaces/{workspaceId}/firewall/retry` 重試 |
| `unavailable` | 部署環境不提供對應 firewall capability | 顯示不可用，不把設定偽裝成成功 |

Runtime 與 Browser 是不同 policy group，任一方開啟都不能放寬另一方。`specific` 只接受 canonical exact hostname；不接受 wildcard、URL、路徑、連接埠或 IP，且 `github.com` 不隱含任何子網域。disabled 仍保留到 kube-dns 的 TCP／UDP 53，但不能產生 world 或 FQDN 對外 allow；specific 使用 `toFQDNs.matchName`，all 才可使用 `toEntities: world`。

## Helm-only execution-plane resource baseline

Workspace Runtime、Browser 與 Canvas 的 Kubernetes request／limit 只由 Helm values、schema 與 render contract 定義，再由 Manager 寫入 Workspace CR、Operator原樣套到 Deployment。Frontend 與 Manager API／DB 都沒有 per-Workspace resource override，也沒有另一份 Python default。

| 元件 | CPU request | CPU limit | Memory request | Memory limit |
| --- | ---: | ---: | ---: | ---: |
| Runtime | `500m` | `2000m` | `1Gi` | `3Gi` |
| Browser | `500m` | `2000m` | `1Gi` | `2Gi` |
| Canvas | `100m` | `1000m` | `1Gi` | `2Gi` |

部署 preflight 會用 node allocatable 與現有 request 驗證至少一個完整 execution plane 可排程；無節點符合時必須在升級前失敗。

## 管理者診斷順序

診斷時應沿同一 revision lineage 比對，而不是只看單一 Pod 是否 Running：

1. 從 Manager availability 取得 stable reason、current `runtimeInstanceId`、access desired／observed revision 與 KB last-known-good revision。
2. 檢查 lifecycle、mount、access 或 firewall durable job 的狀態、target revision、lease、heartbeat 與 fencing token；superseded lineage 不得覆寫最新 observed state。
3. 比對 Workspace CR 的 spec desired revision、status observed revision、component phase、reason、error code 與 workload identity。
4. 防火牆先比對 Workspace target delivery ID、CNP UID／generation／Rule marker 與 selected Pod／CiliumEndpoint identity，再檢查每節點 attestation 的 agent incarnation、observed／expires time、realized policy revision 及完整 endpoint set；不能用 CNP `Valid` 或 CEP `enforcing` 替代。
5. 比對 Runtime 與 Browser policy group，以及 disabled／specific／all 的 DNS 與 egress 規則。
6. 若 DB 顯示 running 但 CR／workload 已不存在，先讓 reconciliation 建立 successor 或明確失敗，不以手動改 DB 製造假成功。

實際查詢應使用部署環境提供的受控管理介面與 namespace；文件不保存 kubeconfig、token、主機名稱或其他環境機密。

## Kubernetes 平台狀態

可攜契約可套用到 EKS／EFS、GKE／Filestore、AKS／Azure Files、OCP／CephFS 或 NFS、RKE2／RWX，以及原生 Kubernetes 搭配 generic NFS／其他 RWX CSI。所有候選環境都必須維持：

- 同一 `workspaceRuntimeNamespace` render
- Workspace 與 KB RWX storage contract
- Manager state PVC 與最小 namespace RBAC
- 固定唯讀 KB mount、各 component `Recreate` fence 與 security context assertion
- 無 privileged、`anyuid`、Runtime `hostPath` 或固定 `runAsUser`
- Manager／Runtime 任意 UID image 契約

本機 runner、Helm render 或 image preflight 不能代替實際平台證據。EKS、GKE、AKS、OCP、RKE2 與原生 Kubernetes 必須分別在目標叢集與實際 CSI／CNI／security policy 上完成 attach、唯讀拒寫、跨 node、recycle、故障恢復與權限測試；沒有該環境 artifact 時，只能稱為符合可攜契約的候選設定，不能稱為 conformance-verified 或正式認證。

## 不採用的方案

- 複製 KB 到 Workspace：會增加資料重複、同步與刪除一致性問題。
- filesystem materializer／projector：本需求不需要 Workspace 專屬副本。
- KBFS sidecar／FUSE：需要額外處理 cache、locking、rename、失敗與安全權限。
- 自製 CSI driver／NFS namespace controller：既有 CSI／NFS driver 已負責 volume lifecycle。
- per-user Runtime：增加資源與 session orchestration 複雜度，且不符合 Workspace 分享後共用內容的產品語意。
- collaborator direct KB 權限交集：會讓新成員的 direct KB ACL 反向拆除既有 Workspace grant。

## 儲存容量 ownership seam

Runtime 只擁有實際使用量量測。Manager 的 `platform_resource_capacity` module 擁有風險 policy、freshness、storage kind、持久化 CR desired state revision、quota、expansion lifecycle 與 projection；Workspace custom-resource module 只是 transport adapter。Operator 只將 CR desired capacity reconciliation 成 PVC request，並回報 observed revision、allocated bytes 與穩定 error code，不擁有 lifecycle terminal policy。Manager 不直接輪詢 PVC，Frontend 也不從 allocated bytes 猜測 provisioner 能力。完整狀態機見[平台資源統計與容量治理](/features/platform/resource-statistics-and-capacity)。
